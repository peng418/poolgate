# 04 · 「不跳转登录」可行性调研（扫码 / 验证码）

> 问题（2026-09-25 用户提出）：能不能不跳转浏览器登录，直接嵌进我们的软件里，能扫码扫码、能验证码验证码？
>
> 结论先说：**iframe 嵌上游登录页这条路走不通**（有硬性禁止，也有绕不过的第三方 Cookie 限制）；
> **但「不跳转」是可以做到的** —— 做法是把授权流搬进面板自己显示：**面板里出一个二维码，
> 用户用手机扫、在手机上完成登录，桌面全程零跳转**。设备码流与 state 轮询流的渠道都能这么干，
> 不需要逆向任何上游接口。真正做不到的只有「在我们软件里直接填手机号收验证码」，
> 因为那要绕过上游的风控 SDK（阿里/腾讯/字节三家都在用）。

## 1. 六家渠道的授权机制与实测

授权地址是让面板 `/api/login/start` 真实返回的（不是看代码猜的）：

| 渠道 | 授权机制 | 面板拿到的授权地址 | 授权页响应式 | 页面里的风控 SDK |
|---|---|---|---|---|
| QoderCN | OAuth **设备码流** | `qoder.com.cn/device/selectAccounts?nonce=…&challenge=…` | ✅ viewport | **阿里**：`cloudauth-device`、`captcha-open`、`static-captcha` |
| QoderCOM | OAuth **设备码流** | `qoder.com/device/selectAccounts?…` | ✅ | 同上（同框架，仅域名不同） |
| WorkBuddyCN | `auth/state` + 浏览器轮询 | `www.codebuddy.cn/login/?platform=CLI&state=…` | ✅ | **腾讯 OneID**：`vendor-oneid-*.js`（3.5MB） |
| WorkBuddyAI | 同上（国际版） | `www.workbuddy.ai/login/?platform=CLI&state=…` | ✅ | 腾讯 OneID（1.3MB） |
| TraeWork | 授权码 + **本机回调** | `www.trae.cn/authorization?auth_callback_url=…&auth_type=local` | ✅ | **字节**：`sdk-glue.js`（客户端安全 SDK） |
| 千问办公 | OAuth 授权码 + PKCE + **本机回调** | `qwenwork.cn/oauth2/auth?client_id=qwenwork-desktop-app&…` | ❌ 无 viewport | **阿里**（网页扫码要 `bx-ua`/`bx-umidtoken`/`bx-et` 设备指纹，实测不可复现） |

### 1.1 能不能 iframe 嵌上游登录页？—— 分两种，但结论都是「别走这条」

- **QoderCN 明令禁止**（实测响应头）：
  ```
  x-frame-options: SAMEORIGIN
  content-security-policy-report-only: … frame-ancestors 'none'; …
  ```
  任何外部页面都嵌不了它的登录页。
- **codebuddy.cn / workbuddy.ai / trae.cn 没设禁止头**（200，无 `x-frame-options`、无 `frame-ancestors`）——
  技术上能嵌，但**登录态拿不回来**：现代浏览器在 iframe 里阻止/分区第三方 Cookie 与 Storage
  （Safari、Firefox 默认阻止，Chrome 也在推进），而这些登录页完全依赖自家域下的 Cookie + localStorage；
  再加上页面内的风控 SDK 可能检测被嵌。**上游还可能随时补上 XFO**，今天能嵌明天就不能。
- 另外：面板本身就在飞牛桌面窗口（可能是 iframe）里，再套一层更容易被浏览器策略收拾。

### 1.2 有没有现成的「扫码 / 验证码接口」可以自己调？

- **扫码**：codebuddy 的登录页 JS 里能搜到 `扫码`（18 处）、`二维码`（2 处）——腾讯 OneID 的扫码登录；
  trae 走字节自己的登录。**接口是有的，但都带风控签名**（腾讯 `beacon`/`oneid`、字节 `sdk-glue`），
  服务端直接调 = 复现别人的风控签名，工作量大、随时会断，而且有绕过风控的条款风险。
- **验证码**：codebuddy/workbuddy.ai 的 OneID 包里 `手机号`（284/189 处）、`验证码`（160/54 处）、`滑块` 都在
  ——说明「手机号 + 验证码」是它们的登录方式之一，但**同理卡在风控 SDK + 滑块**上。
- 千问办公的扫码这条路 2026-09-24 已经实测死过：网页版 QR 登录要阿里设备指纹，
  空值/假值一律 `invalid QR login request`，服务端复现不了（见 `src/README.md`）。

### 1.3 一个有用的副产品：TraeWork 的回调地址是**我们指定的**

```
https://www.trae.cn/authorization?auth_callback_url=http%3A%2F%2F127.0.0.1%3A40487%2Fauthorize&auth_from=solo&auth_type=local
                                 ↑ 这个参数由我们传；实测传局域网地址也返回 200（没被拒）
```
也就是说：把回调改成**面板自己的局域网地址**（如 `http://192.0.2.10:5014/authorize`），
手机扫码或别的电脑的浏览器都能把授权码送回来 —— 「必须浏览器与 PoolGate 同机」这条限制**是可以去掉的**。

对照：**千问办公不行**，它的 `redirect_uri` 必须在客户端预注册清单里（实测传局域网地址得到）：
```
HTTP 302 → /oauth2/fallbacks/error?error=invalid_request
  error_description: … The 'redirect_uri' parameter does not match any of the OAuth 2.0 Client's pre-registered redirect urls.
```

## 2. 三条路线的评估

| 路线 | 能不能嵌 | 结论 |
|---|---|---|
| **A. iframe 嵌上游登录页** | Qoder 禁止；其余能加载但拿不回登录态（第三方 Cookie/Storage 分区 + 风控 SDK + 上游可随时收紧） | ❌ 不作为方案 |
| **B. 给面板套原生壳（Electron/Tauri）**，用顶层 webview 嵌登录页 | 技术上可行（顶层窗口没有第三方 Cookie 问题） | ❌ 交付形态不允许：飞牛 FPK 只能「Go 服务 + 网关桥显示的网页」，发不出原生壳；成本也远超收益 |
| **C. 把授权流搬进面板：出二维码 + 轮询** | 不需要嵌任何页面 | ✅ **推荐**，见下 |

## 3. 推荐做法：面板内二维码（扫码在手机上完成，桌面零跳转）

原理：这些渠道的授权本来就是**「另一台设备完成、我们轮询结果」**——设备码流天生如此，
state 轮询流也一样（页面登录完回写 state，我们 poll 到 token）。所以只要把授权地址**画成二维码**，
用户拿手机扫一下、在手机上完成登录，桌面这边什么都不用跳。

| 渠道 | 落地动作 | 难度 |
|---|---|---|
| QoderCN / QoderCOM | 把设备码地址渲染成真二维码（现在面板上那个是**装饰性的假二维码**）+ 保留「打开授权页/复制链接」兜底 | 小 |
| WorkBuddyCN / WorkBuddyAI | 同上（state 轮询地址） | 小 |
| TraeWork | 同上 **＋ 回调地址从 `127.0.0.1` 改成面板的局域网地址** → 手机扫码后回调直接回到 NAS | 中 |
| 千问办公 | redirect_uri 锁死在 `127.0.0.1`（上游预注册），二维码解决不了远端浏览器；**加「粘贴回调地址」兜底**：把浏览器地址栏那串贴回面板，服务端拿里面的 code 换 token | 中 |

### 3.1 明确不做的

- **服务端复现各家的扫码/验证码接口**：要复现腾讯/字节/阿里的风控签名与设备指纹，
  工作量大、上游一改版就断，且属于绕过风控 —— 不做。
- **在上游页面外收集手机号/验证码**：同上，且会让用户的凭据经过我们（现在凭证只在我们与上游之间）。

### 3.2 落地情况（2026-09-25 已实现，v0.4.0）

- **P1 面板内真二维码**：✅ 已实现（`qrcode.js` vendored；实测把渲染出的码**解码**回授权地址，
  QoderCN 与 TraeWork 都解得出来）。
- **P2 TraeWork 回调改面板地址**：✅ 已实现（`channel.LoginOptions.CallbackBase`），
  实测扫码内容里的 `auth_callback_url=http://192.0.2.10:<port>/authorize`。
- **P3 千问办公「粘贴回调地址」兜底**：✅ 已实现（`channel.CallbackAcceptor` + `POST /api/login/callback`），
  千问的授权页不出二维码、直接给锁本机提示与粘贴框。
- 仍不做：iframe 嵌上游登录页、服务端复现扫码/验证码接口（理由见 §1.2 / §2）。

### 3.3 原建议的落地顺序

1. **P1**：面板授权视图渲染真二维码（四家 + TraeWork 通用）。需要引入一个纯 JS 的二维码编码器（vendored，约 10KB）。
2. **P2**：TraeWork 回调地址改为面板局域网地址（去掉同机限制），并把「用手机扫码完成」写进界面文案。
3. **P3**：千问办公「粘贴回调地址」兜底（顺带解决它远端浏览器完全无法授权的现状）。
4. 之后再评估：把「扫码完成」做成默认路径（打开面板即出码），「打开浏览器」降为兜底。

## 4. 复核用的实测命令

```sh
# 六家的授权地址（真实调用，非猜测）：登面板后
curl -b ck -X POST -H 'Content-Type: application/json' -d '{"channel":"qodercn"}' $PANEL/api/login/start

# 是否能被 iframe 嵌入
curl -sS -o /dev/null -D - -A 'Mozilla/5.0' 'https://qoder.com.cn/device/selectAccounts?nonce=1&challenge=x' | grep -i 'x-frame-options\|frame-ancestors'

# 千问的 redirect_uri 是否可换成局域网地址（结论：不可以）
curl -sS -o /dev/null -D - 'https://qwenwork.cn/oauth2/auth?client_id=qwenwork-desktop-app&response_type=code&scope=openid&redirect_uri=http%3A%2F%2F192.0.2.10%3A5014%2Fcallback&code_challenge=x&code_challenge_method=S256&state=abcdefgh' | grep -i '^location'

# TraeWork 的回调参数是否可换成局域网地址（结论：接受）
curl -sS -o /dev/null -w '%{http_code}\n' -A 'Mozilla/5.0' 'https://www.trae.cn/authorization?auth_callback_url=http%3A%2F%2F192.0.2.10%3A5014%2Fauthorize&auth_from=solo&auth_type=local&channel_name=common'
```

> 注：上游随时可能改。本页结论是 2026-09-25 的实测快照；判定「能不能嵌」要看响应头，别只看页面能不能打开。
