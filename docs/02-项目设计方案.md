## 1. 设计原则

| 编号 | 原则 | 落地方式 |
|---|---|---|
| D1 | **失败必须可见** | 错误只有一个出口：结构化 `ErrKind` + 客户端可见 + 落流水。任何 `_ =` 丢弃错误的写法在 CI 里禁止 |
| D2 | **健康 = 收到有效内容** | 所有健康判据统一走「探测 → 收到首个 content/`[DONE]` 才算通过」 |
| D3 | **渠道可插拔** | 渠道 = 一个 adapter 包 + 一份能力声明；核心层零 `if channel == "xxx"` |
| D4 | **单一错误模型** | 上游千奇百怪的错误在 adapter 内归一成有限枚举，路由层只认枚举 |
| D5 | **凭证与配置分离** | 凭证单独加密文件、权限 600、永不入日志/导出；配置可明文导出 |
| D6 | **交付形态不变** | Go 单二进制 + `go:embed` 前端 + fnOS FPK；数据目录沿用现网约定 |

**分层职责（单向依赖，下层不知道上层）**

| 层 | 职责 | 不知道什么 |
|---|---|---|
| Gateway | 协议兼容、鉴权、清洗、错误回传 | 不知道渠道存在 |
| Router | 选号、重试、冷却 | 不知道渠道协议 |

| Pool | 账号状态、凭证生命周期、签到保活 | 不知道 HTTP |
| Store | 落盘、加密、缓存 | 不知道业务 |

## 3. 渠道适配器契约

```go
// Channel 一个渠道的完整能力面。实现方只需关心「怎么和这个上游说话」。
type Channel interface {
    Kind() Kind                          // qodercn / workbuddy / traework ...
    Spec() Spec                          // 能力声明（见下）

    // 凭证
    Login(ctx context.Context) (Credential, error)  // 登录流程（可弹浏览器）
    Refresh(ctx context.Context, c *Credential) (*Credential, error)

    // 对话：返回标准 OpenAI chunk 流；协议差异全部在这一层消化
    Chat(ctx context.Context, c *Credential, req ChatRequest) (Stream, error)

    // 目录与账务
    Models(ctx context.Context, c *Credential) ([]ModelInfo, error)
    Pricing(ctx context.Context, c *Credential) ([]ModelPricing, error)
    Balance(ctx context.Context, c *Credential) (Balance, error)
    Checkin(ctx context.Context, c *Credential) (CheckinResult, error)

    // 错误归一：上游 -> 有限枚举
    Classify(status int, body []byte) ErrKind
}

// Spec 能力声明：UI、网关清洗、模型下发全部读它。
type Spec struct {
    Kind            Kind
    DisplayName     string   // QoderCN / WorkBuddyCN / TraeWork
    Status          Status   // Active / Paused / Maintenance
    SupportsTools   bool
    SupportsImages  bool
    SupportsReasoning bool
    SSEOnly         bool     // 上游只有流式 → 非流式由本地聚合
    Cooldown        CooldownPolicy  // 各 ErrKind 的冷却时长
    // 凭证形态、登录方式、签到能力等
}
```

**新增一个渠道的完整成本** = 新包实现 `Channel` + 一行注册：

```go
registry.Register(qodercn.New(), qodercn.Spec())
```

**摘除一个渠道的完整成本** = 把 `Spec.Status` 改成 `Paused`（或删掉注册行）。
这正是千问办公事件需要的操作粒度。

## 4. 统一错误模型

上游的错误形态五花八门（信封包 200、`code 112`、`429`、TLS 超时……），
**归一成有限枚举**，路由与 UI 只认枚举：

| ErrKind | 含义 | 默认处置 | 冷却 |
|---|---|---|---|
| `HardCredit` | 余额/权益不足 | 冷却该号 | 12h |
| `SoftRate` | 限流（429） | 冷却该号 | 60s |
| `Muted` | 账号被上游**禁言**（风控/违规处置，报文带 `mute_until`） | 冷却该号**到上游给的解禁时间**（上游没给才用 30m 兜底）；**不禁用、不续期**——禁言不是凭证问题 | 至解禁时间 |
| `SessionDead` | 会话/签名失效（401、`Signature invalid`） | 禁用该号，提示重登 | — |
| `ContentBlocked` | 内容拦截 | **不冷却**，透传原文 | — |
| `PromptTooLong` | 超出上下文 | **不冷却**，透传原文 | — |
| `ModelUnavailable` | 该账号无此模型权限 | 软冷却 + 模型级标记 | 10m |
| `UpstreamFault` | 上游 5xx / 闸门 / 目录不可用 | 渠道级降级告警，**不计账号错误** | 5m（渠道级） |
| `Transport` | 连不通 / TLS / 超时 / **上游连接中断**（收到内容前断流） | **推断类**：先计数，连续到门槛才**软冷却**（仍会被选用，一次成功即解除）；单账号渠道不冷却 | 门槛 + `err_cooldown`（10m） |
| `Parse` | 响应无法解析 / 上游 200 但空流 | 同上（推断类，走连续错误门槛） | 门槛 + `err_cooldown`（10m） |
| `SessionBusy` | 上游同一账号的**会话启动**还在处理中（`409 CONCURRENT_OPERATION`） | **不冷却**：适配器内退避重试（400ms→1.2s），仍失败才回 503 | — |

**关键区分**：`UpstreamFault` 与账号健康解耦。千问办公的 `503 Model catalog unavailable`
属于渠道级故障——以前它会被当成账号错误累积，导致误判为「号坏了」。

**错误分两类：上游明确裁决 vs 本地推断（0.9.9，`errs.Kind.Inferred()`）**

| 类别 | 判据 | 处置 |
|---|---|---|
| **上游明确裁决**（`SoftRate` / `HardCredit` / `Muted` / `SessionDead` / `ModelUnavailable`） | 上游已经给了判决，重试没有余地 | 立即按 Policy 冷却/禁用；**不接受**「探通了就提前放开」（额度不足冷 12 小时，探一次恰好通了就解冻，下一波请求又整片 402 = 拿用户的请求当探针烧） |
| **本地推断**（`Transport` / `Parse`） | 单次发生不足以判定账号坏（网络抖动、上游抽风） | ① 先计数，**连续 `err_threshold` 次**才冷却 `err_cooldown`；成功即清零；② 冷却属**软冷却**：该号仍可被选用（排在健康号之后），**一次成功即自动解除**；③ 池里只有一个可用账号的渠道**不冷却**（冷它 = 整条渠道下线） |

`err_threshold` 门槛（出厂 5 次 / 冷却 10 分钟）对齐参考实现 wild-work 的 `cooldown` 配置块
（`err_threshold` + `err_cooldown`）——当初移植 `Cooldown` 时把这个门槛整个丢了，
于是退化成「一错即冷」，一次抖动就能把整条渠道冻住。**「成功即解除」也是参考实现的做法**
（wild-work 的 `ReenableIfCredits`：签到/余额同步成功后直接清 `until`），PoolGate 现在
在 `Pool.NoteSuccess` 里做同一件事，并且体检/路由的成功回写都走它。

**`Transport` 与账号健康的关系（两段历史，别只看其中一段）**：0.9.8 之前它一次抖动就冷号
10 分钟（真机事故：两个号一起冷掉 → 整渠道 `503 NoCandidate` 十分钟，而 38 秒前的体检还是绿的）；
0.9.8 改成完全豁免（连「一直在断的号」也记不下来）；0.9.9 起恢复**计数 + 门槛**，
这才是与参考实现逐字对齐的形态。「要不要冷却这个号」与「要不要换号」仍是两个判据
（`errs.Kind.AccountBlamed()` / `errs.Kind.StopRetry()`）。

**`SessionBusy`（2026-09-27 真机实测）**：对真上游连发 4 次 `POST /api/chat-sessions` ——
`+0.0s → 201`、`+0.2s → 409 CONCURRENT_OPERATION`、`+2.4s → 201`、`+4.0s → 201`。
闸门只挡「前一次启动还在处理中」的那一两秒。它以前落在限流词表里 → 判成 `SoftRate` →
冷却该号 60 秒 → 单账号渠道等于整条渠道冻结一分钟（用户投诉的「一直冻结」就是这个）。
现在：单独归 `SessionBusy`，**不冷却**，适配器内退避重试并落日志。
同一账号的会话令牌也从 `sync.Mutex` 换成可取消信号量 —— 等不到就明确报「账号忙」，
而不是把请求冻死在锁上。

**`NoCandidate` 的结论必须自带处置所需的事实**：`503` 的 message 不是一句「可能全部冷却或禁用」，
而是逐号列出运行态（`9567c2c8 冷却至 09-27 00:03（到点自恢复）；700f4798 已禁用（SessionDead），
需重新授权或手动启用`）。网关与面板体检共用 `pool.ReasonNoCandidate` 同一句话，不许两边说法不一。

**可见性契约（硬性）**：

| 时机 | 行为 |
|---|---|
| 响应头未发出 | 返回结构化 JSON 错误（HTTP 502/503 + `ErrKind` + 上游原话） |
| 响应头已发出、无内容 | 写 SSE 错误帧 + `[DONE]`，**不允许静默关闭** |
| 任何时候 | 落一条流水（渠道/账号/模型/ErrKind/耗时/上游报文摘要） |

## 5. 路由与健康

### 5.1 选号

```
候选 = 渠道可用账号 − 已禁用 − 本请求已试过
排序 = 健康分(近期成功率、TTFT)　−　粘性命中加权　+　余额权重
       （推断类「软冷却」的号排到最后，而不是排除 —— 见 §4）
```

- **粘性**：会话 ID → 账号 uid 映射（默认 50 次请求/账号），命中则优先复用，降低风控。
- **轮转**：失败自动换号，上限可配；换号即清粘性。
- **健康分**：滑动窗口统计（近 20 次），失败率 > 阈值则降权而非直接禁用（避免误杀）。

### 5.2 健康探测（D1/D2 的落点）

```
探测 = 每渠道取 N 个代表模型 → 发真实请求（stream, max_tokens 小）
判据 = 收到首个 content/reasoning delta 或 [DONE]  → 通过
       空流 / 信封错误 / 超时                        → 失败，记录上游原话
结果 = 渠道状态（可用/降级/故障/暂停） + 模型健康度 + 可审计的「为什么」
```

- 定时（默认 6h）+ 变更后自动触发。
- 结果持久化，面板可直接引用（F5.5）。**测速与体检共用同一套判据**，避免两套逻辑打架。
- **「无可用账号」必须自己解释原因**：这种情况下的结论要带上该渠道每个账号的运行态
  （谁在冷却到什么时候 → 到点自恢复；谁被禁用、按什么原因禁用 → 需重新授权或手动启用）。
  只报一句「无法探测」，用户连该等还是该动手都判断不了（2026-09-26 真机教训）。
  文案本体在 `pool.ReasonNoCandidate`：**体检与网关 503 用同一句话**，
  否则客户端说「冷却自恢复」、面板说「已禁用」，用户不知道该信哪个（2026-09-27 补）。

## 6. 数据模型与目录

沿用现网约定（迁移期与 wild-work 并存不冲突），应用名 `poolgate`：

```
/vol6/@appcenter/poolgate/          # 应用（FPK 安装）
  bin/poolgate                      # 单二进制
  ui/                               # 面板静态资源（go:embed 兜底）
/vol6/@appconf/poolgate/
  creds/<channel>-<uid>.json        # 凭证（600，含 refresh_token）
/vol6/@appdata/poolgate/
  config.json                       # 非敏感配置（监听/API Key/策略）
  state-<channel>.json              # 账号运行态（余额/冷却/签到）
  requests.db                       # 请求流水（SQLite，可滚动清理）
  health.db                         # 体检/测速历史
  cache/{models,pricing}.json       # 目录与费率缓存
```

**凭证加密**：`creds/*.json` 用本机密钥（首次生成，存 `/vol6/@appconf/poolgate/key`，600）
做 AES-GCM 封装；导出功能默认剔除凭证。

## 8. 前端架构与设计系统

### 8.1 技术栈选型

| 项 | 选择 | 理由 |
|---|---|---|
| 框架 | **Vue 3 + Vite + TypeScript** | ← **已确认**（§11）。wild-work 手写 `app.js` 单文件 2200+ 行、一次改版 diff 2201 行（实测），已达可维护性上限；Vue 与 Hermes Studio 同栈，组件与设计语言可复用 |
| 产物 | 构建后 `go:embed` 进二进制 | 保留「单文件交付、无外部依赖」的优点，不引入运行时 |
| 图表 | 轻量 SVG 手写（不引图表库） | 本项目图表简单（条形/趋势/状态块），引库反而变重 |
| 截图回归 | Playwright + Chromium | 已有工具链（`/usr/bin/chromium`），改动后自动出图对比 |

### 11.1 补充裁定：控制台登录（需求 P6 的落点）

wild-work 的实测教训里记着一条 P6：**模型列表里已有用户，却没有登录入口，加不进新账号**。
这不只是少一个按钮——「加号」是账号池的入口，没有它池子只会慢慢枯竭（需求 §7「账号来源不稳定」风险）。

**范围裁定**：

- 做**单管理员密码**登录，**不做**多用户/注册/找回密码/角色权限（需求 N1、N6）。
  忘记密码走命令行 `poolgate admin reset-password`。
- 首次运行（无管理员账号）进入**设置密码向导**；判据是「密码文件不存在」，不是「有没有用户表」。
- 渠道授权与控制台登录是**两件事**：前者是往池子里加上游账号（OAuth），后者是进面板（本地密码）。
  原型 `07-login.html` 两个流程都给了，但后端是两套接口。
- 授权失败屏必须给出 `ErrKind` + 上游原话——这是红线一（零静默失败）在 UI 上的直接体现，
  不接受「授权失败，请重试」这种无信息文案。

**会话与接口**：

| 端点 | 用途 | 备注 |
|---|---|---|
| `GET /api/session` | 当前会话状态 | 未登录 → 401，前端跳登录页 |
| `POST /api/session` | 密码登录 | 失败计数 5 次 → 锁 15 分钟；计数与来源 IP 落日志 |
| `POST /api/setup` | 首次设置密码 | 仅在无管理员账号时可用；之后永久关闭 |
| `POST /api/login/{kind}/start` · `/cancel` | 发起/取消渠道授权 | 见 §7 |

凭证以 Argon2id 哈希存放；会话为 HttpOnly Cookie（记住我 = 30 天）。
**面板登录不等同于渠道凭证**——即使管理员密码泄露，导出的配置包默认仍不含上游 token（D5）。

## 12. 接入源架构裁定（2026-09-25）

**背景**：渠道从「只有 IDE/助手类平台（登录授权）」扩展到「官方 API（填 API Key）」，需要裁定
「多来源是走一个入口还是各自一个入口」，以及面板怎么放。调研依据见
[`docs/05-可接入平台调研.md`](05-可接入平台调研.md)，原型见 `prototype/08-providers.html` 与 `prototype/09-provider-add.html`。

### 12.1 裁定：**统一入口，不做单独调用**

```
客户端（Studio / Claude Code / 任意 OpenAI SDK）
        └── 只认一个地址 + 一个 API Key：http://<NAS>:5014/v1
                        ↓
   PoolGate 按模型名的来源前缀分发：qodercn/glm-5.3 · traework/Doubao-Seed-2.1-Pro · google/gemini-3.8-flash
```

理由（按重要性）：

1. **池化只在单入口成立**：多号/多 key 轮换、失败冷却、限速排队、换号重试、粘性会话、
   统一日志与健康判据 —— 全都要在「同一个入口能看到所有候选」的前提下才做得成。
2. **客户端零改动**：换供应商、加渠道都不用改客户端配置；这在「Studio 里配 provider」这种场景是硬需求。
3. **既有架构已经如此**：现有 6 个渠道靠 `<渠道>/<模型>` 前缀分发（`gateway.parseModel`），
   key 式来源直接沿用同一规则，核心层零渠道专有代码（红线三）。
4. **分开的只是管理界面**：列表/额度/健康按来源分组展示，调用入口永远一个。

配套两个开关（都在设置页，默认值保持现有行为）：

| 开关 | 作用 | 默认 |
|---|---|---|
| 模型别名 | 给 `google/gemini-3.8-flash` 这类长名配短名（如 `gemini-flash`） | 空 |
| 默认来源 | 不带前缀的裸模型名走谁 | QoderCN（保持现状） |

### 12.2 面板信息架构调整

| 页面 | 变化 |
|---|---|
| **接入源**（新，一级导航，排在「总览」之后） | 登录式渠道 + API Key 式来源**混排一张表**；类型列区分「登录授权 / API Key」；额度列分「余额 / 配额 / 限速」三态并各自写明恢复方式 |
| 添加接入源（新，向导 3 步） | 选类型 → 填参数（预设模板自动带 base_url、从上游拉模型清单、声明工具调用能力）→ **连通性测试**（鉴权 / 目录 / 工具调用 / 延迟）后保存 |
| 账号 | 不变（仍是按来源分组的登录账号管理） |
| 模型与费率 | 加「来源」列，支持按来源分组 |
| 设置 | 只保留跨来源的通用项（含上面的两个开关） |

### 12.3 新增来源的落地顺序

1. **通用 OpenAI 兼容上游适配器**（`internal/adapter/openaiup`，配置级）—— 一次覆盖 22 家官方 API；
2. **接入源页**（把两类来源并到一张表，含向导与连通性测试）；
3. **腾讯 CodeBuddy**（同族 C 类第一个真渠道：与现有 WorkBuddy 共用腾讯系授权，社区有现成逆向项目）。

> 硬前提两条（写进验收）：① 任何新来源进池前必须实测**能不能给结构化 `tool_calls`**（拿不到就只能当聊天，不能做 coding agent 后端）；
> ② 不支持的必须**明确拒绝并给原因**，不许像 0.4.2 之前那样静默丢弃（F3.7 / 红线一）。
>
> 工具能力在 `channel.Spec` 里声明，分四档：原生（`Tools`）/ 网关代做模拟（`ToolsShim`）/
> **忽略（`ToolsIgnore`）**/ 都不声明 → 明确拒绝。前三档对客户端的 tools 合同都不变
> （第 3 档拿到的是自然语言回答，不会有 tool_calls）。**忽略档只给「纯文本入口」用**
> （现为千问办公：工具由上游自己那套内置能力承担），必须同时落一条日志，默认行为仍是拒绝。
