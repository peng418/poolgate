# 06 · 网页渠道框架与防封号设计

> 目标：**主流厂商都能接**（网页登录式），并且把「防封号」做成框架能力，不是每家自己想办法。
> 与 `docs/05` 的分工：05 是「哪些平台能接」的可行性调研，本文是「怎么接、怎么不被封」的设计。

---

## 1. 先认清三个分水岭（决定可行性的不是代码）

| 分水岭 | 说明 | 影响 |
|---|---|---|
| **① 出网 IP** | 本机出口是机房 IP → Cloudflare 系（chatgpt.com / perplexity / mistral 网页）直接挑战，Meta/Anthropic 按 IP 拒 | **C 类厂商的前置条件**：没有住宅/家宽出口，写出来也用不了 |
| **② 反爬强度** | 有的签名能服务端复现（Qwen OAuth、DeepSeek PoW、iFlow HMAC、智谱 md5 签名）；有的**在浏览器里现算**（豆包 `a_bogus`、ChatGPT sentinel PoW） | **判据修正（0.5.0）**：「签名必须在浏览器里算」**不等于**做不了 —— 凭证由用户从浏览器里粘出来（Cookie / token / 请求头），签名那一步要么根本不带（豆包纯 HTTP 路径）、要么在服务端照算法重算（ChatGPT 的 PoW 是可复现的）。真正决定成本的是「要不要**常驻**无头浏览器」，而我们选了不做无头浏览器 |
| **③ 上游是否支持工具调用** | 原生支持的：Qwen `/cli`、Claude（Messages API）、CodeBuddy、Copilot、Kiro、iFlow、灵码、Antigravity；**不支持的**：豆包、元宝、Kimi、智谱、DeepSeek 网页、ChatGPT 网页、Windsurf | **判据修正（0.5.0）**：不支持**不构成排除理由** —— `internal/toolshim` 把 `tools` 翻成提示词、再把模型输出的标记解析回结构化 `tool_calls`，对客户端合同不变（0.4.4 起就有）。前提是**面板必须如实标注**哪档是原生、哪档是模拟（靠模拟的那几家已经在 `Spec.Docs` 里写明） |

## 2. 厂商矩阵（按接入方式分四档）

| 档 | 含义 | 厂商 |
|---|---|---|
| **A · 配置级**（已实现） | 官方 OpenAI 兼容 API，填 `base_url`+`key` | OpenAI、Gemini、DeepSeek、Kimi、智谱、百炼、火山方舟、混元、千帆、MiniMax、硅基流动、魔搭、OpenRouter、Groq、Together、Fireworks、Cerebras、xAI、Mistral、NVIDIA NIM…（约 22 家） |
| **B · 登录授权式，签名可服务端复现** | 现成活跃项目 + 不需要浏览器 | **通义 Qwen**（`/cli` OAuth，819★ 活跃）、**DeepSeek**（PoW 可解，752★）、**Kimi**（JWT 可刷新，240★）、**智谱清言**（63★，薄）、**z.ai**（有官方免费 Key，不必逆向） |
| **C · 需要真实浏览器指纹 / 好 IP** | 签名在浏览器里现算，或 IP 被 Cloudflare 挑 | **已做（0.5.0）**：豆包、腾讯元宝、ChatGPT 网页（凭证粘出来 + 必要签名在服务端重算，不带 `a_bogus`）；**仍在观察**：Perplexity 网页、Mistral 网页、Grok 网页 |
| **D · 不做** | 站点不可达 / 无可用项目 | 跃问（`yuewen.cn` 不可达）、纳米 AI、秘塔（搜索型）、海螺（无文本逆向） |

**关于 ChatGPT**：它能做（`chat2api` 3.8k★、`gpt4free` 66.7k★ 都还在维护），但**必须同时满足**
① 干净的住宅 IP（本机机房 IP 现在直接被 CF 挡）、② 账号 access token + 设备指纹、
③ 接受封号风险。**它排在最后**：不是技术不行，是前置条件最多。

## 3. 防封号设计（框架能力，每家自动受益）

封号从来不是单一原因，而是「同一账号在多处露出破绽」。逐条对应到 PoolGate 的机制：

| 风险 | 机制 | 落点 |
|---|---|---|
| **多账号同一出口 IP** → 关联封禁 | **每账号绑定独立出网代理**（`Credential.Extra["proxy"]`） | `channel.NewHTTPClient` 按凭证建客户端；代理可留空（直连） |
| **同一账号被并发打** → 行为异常 | **每账号串行 + 最小请求间隔**（可配） | `pool.Gate`（新）：取号后占槽，流关闭才释放；间隔不足则排队 |
| **请求太密** → 触发风控 | 每账号独立限速（RPM/最小间隔），与全局限速分开 | 同上，参数进 `store.Settings`（按渠道覆盖） |
| **指纹/设备 ID 复用** → 关联 | 一账号一 `device_id`/指纹/cookie jar（凭证里带，绝不共用） | 各适配器的凭证字段（现有 COSY 系已是这形状） |
| **失败后猛重试** → 从限流升格成封号 | 失败即按 `errs` 分档冷却；**风控类失败不自动重试**（只换号） | `errs.DefaultPolicy` + `router`（已实现，新增"风控类不重试"判据） |
| **把额度榨干** → 异常用量 | 每账号日用量上限（可选）+ 面板可见的「今日已用」 | 请求流水已在记，加上限阈值 |
| **对外提供服务** → 被平台盯上 | 默认**只对本机/局域网**下发；暂停开关一键摘除 | `Spec.Status` + 绑定地址（已有） |

**一条原则**：**宁可少用，不要试错**。任何「不确定是不是风控」的失败，一律冷却 + 换号，
绝不在同一个账号上连续重试 —— 封号通常就是这么试出来的。

## 4. 落地顺序

1. **基础设施（厂商无关，先做）**：`pool.Gate`（每账号串行 + 最小间隔）、`channel.NewHTTPClient`（每账号代理）、
   限速参数进设置、风控类失败不重试。做完每家渠道自动受益。
2. **B 类第一家：通义 Qwen**（`/cli` OAuth + 原生工具调用，参考实现活跃）。
3. **B 类其余**：DeepSeek（PoW）→ Kimi（JWT）→ 智谱清言。
4. **C 类（0.5.0 已完成）**：出网 IP 仍然是**运行环境**的前置条件（本机机房 IP 被 Cloudflare 挡，
   用户自己的网络不受影响）；实现上不再要求「服务端能伪装浏览器」—— 凭证由用户粘出来即可。
   已接：豆包、腾讯元宝、ChatGPT 网页。

> 验收口径（每个网页渠道都跑一遍）：① 面板里能完成登录（扫码/授权）；② 带 `tools` 的请求
> 能拿到结构化 `tool_calls`（原生，或 `toolshim` 模拟且实测稳定）；③ 连续 N 次请求不触发风控；
> ④ 关掉渠道后客户端立刻拿不到它的模型。

## 5. 补充裁定：「A 类官方 API」不等于只能填 key（2026-09-25 追加）

用户的要求很明确：**不要 key，全部走登录**。据此重新审视 `docs/05` §5 的 22 家：

**「登录式」只有三种真实形态**：

1. **网页聊天私有协议** —— 用户用自己的账号登录网页版，我们驱动它的接口（现有 6 个渠道与通义都是这一类）；
2. **官方 CLI 的 OAuth** —— 平台自己发的命令行工具走设备码/授权码，令牌可以喂给第三方（Qwen Code CLI 已做成；Gemini CLI、iFlow CLI 同理）；
3. **云平台控制台登录** —— **不存在**：百炼/方舟/千帆/混元的 API 只认控制台签发的 key，没有「登录即可调用」这回事。

**逐家判定**：

| 能做成登录式的（有消费者登录产品） | 路径 | 现成项目 |
|---|---|---|
| **通义（Qwen）** | ✅ 已做（CLI OAuth + 原生工具调用） | — |
| **DeepSeek** | 网页登录 + 服务端可解的 PoW | `NIyueeE/ds-free-api` 752★ |
| **Kimi** | 网页 JWT（可刷新） | `chopper1026/kimi2api` 240★ |
| **智谱清言** | 网页签名接口 | `xiaoY233/GLM-Free-API` 63★ |
| **Gemini** | **Gemini CLI 的 Google OAuth**（官方路线，日额度大、原生 tools） | `geminicli2api` 591★ |
| **ChatGPT** | 网页逆向（需能过 Cloudflare 的出口；工具调用要靠 `toolshim`） | `chat2api` 3.8k★ / `gpt4free` 66.7k★ |
| **Claude** | 网页逆向（同上，且需干净 IP） | `claude-*` 社区项目 |
| **Grok（xAI）** | 网页 `sso` cookie | 项目零散 |
| **Mistral** | Le Chat 网页（或官方免费层 key） | 无成熟项目 |
| **腾讯元宝** | 网页 `x-uskey`（参考实现已从 13★ 长到 273★，且有第二份独立实现交叉验证帧结构） | **已做（0.5.0）**，思考按 `type=think` 分流 |
| **豆包** | 网页 Cookie + 设备参数；`a_bogus` 由浏览器 fetch hook 现算 | **已做（0.5.0）**：走纯 HTTP 路径（不带 `a_bogus`），风控码归一成「去过验证码」而不是静默失败 |

| **客观做不成登录式的（只有 key）** | 原因 |
|---|---|
| OpenRouter · Groq · Together · Fireworks · Cerebras · NVIDIA NIM · SambaNova / DeepInfra / Novita / Nebius | 纯 API 聚合/推理公司，**没有面向消费者的登录产品**，唯一凭证就是 key |
| 阿里百炼 · 火山方舟 · 百度千帆 · 腾讯混元（API 侧）· 硅基流动 · 魔搭 · MiniMax | 云平台 API 只认控制台签发的 key；它们**对应的消费者产品**（通义网页 / 豆包网页 / 文心 / 元宝）是另一条渠道，要单独按网页协议做 |
| GitHub Models | 已退役 |

**结论（写进范围）**：
- **登录式优先**：上表「能做成」的按 `DeepSeek → Kimi/智谱 → Gemini CLI → ChatGPT/Claude/Grok（需出口）` 顺序推进；
- **key 式来源保留但不推广**：`接入源` 页的通用 OpenAI 兼容适配器照旧可用（用户想用就用），
  但**不作为 A 类的主路径** —— 那批纯 API 平台客观上没有登录路径，硬做只能靠抓控制台会话，收益与风险都不划算；
- 判定口径不变：**能不能给结构化 `tool_calls`**（原生或 `toolshim` 实测稳定）是硬门槛。
