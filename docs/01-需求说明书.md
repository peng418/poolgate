# 01 · 需求说明书

> PoolGate · AI 账号池网关 ｜ 2026-09-24 ｜ 状态：**已确认**（前端 Vue3+Vite · 首发 3 渠道 · 独立应用并存迁移）
>
> 确认结论（2026-09-24）：① 前端栈 = **Vue 3 + Vite + TypeScript**；
> ② 首发渠道 = **QoderCN / WorkBuddyCN / TraeWork**（其余按「暂停」处理，保留适配器位置）；
> ③ 迁移方式 = **独立应用名与数据目录，与 wild-work 并存**，确认稳定后再摘，全程可回退。
> 三项确认已写进 [设计方案 §11](02-项目设计方案.md#11-评审结论2026-09-24)。

## 1. 为什么要做这个项目

### 1.1 现状

`wild-work` 已经跑通了一条完整链路：把多个 AI 编程助手的订阅账号汇成账号池，
对外提供 OpenAI 兼容 API，自带面板做登录/签到/保活/测速。它能用，而且已经在我们自己的
环境里承担真实流量。

### 1.2 问题（都是实测出来的，不是推测）

| # | 问题 | 实证 |
|---|---|---|
| P1 | **静默失败**：上游把错误包在 `HTTP 200` 的 SSE 信封里，流式分支把解析错误丢弃，客户端拿到 `200 + 0 字节` | `internal/server/handler.go` 原为 `_ = rt.Upstream.Stream(...)`；Studio / Claude Code 因此「不回复也不报错」 |
| P2 | **健康判据撒谎**：测速只看 `HTTP 200` 就判 `ok`，空流与错误信封都显示绿色 | 2026-09-24 11:47 全量测速把已废的千问办公 3 个模型标成 `ok ≤667ms` |
| P3 | **渠道堆砌**：7 个渠道里 4 个已不可用，却没有统一的「摘除」机制；渠道逻辑散落在 `internal/<channel>/` + 巨型 `app.go` | 千问办公上游改版后，只能靠人工判断「代码要不要回滚」 |
| P4 | **前端难维护**：单文件 `app.js` 手写 2200+ 行，一次 UI 改版的 diff 就有 2201 行 | `git diff --stat` r22 提交前的实测 |
| P5 | **无可观测性**：请求级流水、错误分类聚合缺失，出问题只能靠 `grep app.log` | 本次排查千问办公，最后是靠手工手搓 COSY 签名直连上游才定位 |
| P6 | **无登录操作**：模型列表中已存在用户，却没有登录入口，无法添加新账号 | 面板只能管理已有凭证，缺少 OAuth/授权码登录流程 |

### 1.3 结论

不是重写一个「更好的 wild-work」，而是**保留已验证可用的能力，把架构换成不会重犯上面六条错误的形状**。

## 2. 用户与场景

**主用户（唯一真实用户）**：NAS 拥有者。技术能力强，自己维护 fnOS + 软路由 + Docker，
用 Studio / Claude Code / Codex 等客户端消费本服务的 API。讨厌长段落，要结论先行和证据链。

| 场景 | 频次 | 期望 |
|---|---|---|
| S1 加号：把新买的订阅账号接进池子 | 偶尔 | 面板点一下 → 浏览器授权 → 自动绑号 → 立刻可用 |
| S2 用号：客户端（Studio/Claude Code）请求模型 | 每日高频 | 稳定出字；失败时要**看见原因** |
| S3 看账：剩余额度、哪个号快死了 | 每周 | 一眼看到「还能撑多久」 |
| S4 排障：某渠道突然不出字 | 每月 | 面板直接告诉我是**上游问题**还是**本地配置问题** |
| S5 体检：升级/改配置后确认没坏 | 每次变更 | 一键「真实体检」，判据可信 |

## 3. 目标与非目标

### 3.1 目标

- G1 一条真流量链路：客户端 → 网关 → 账号池 → 上游，端到端可用、可观测。
- G2 **失败必须可见**：任何上游异常，客户端拿到结构化错误，面板能看到分类与计数。
- G3 **健康判据可信**：只有收到有效内容才算通过，杜绝假绿。
- G4 **渠道可插拔**：新增/摘除渠道是配置级操作，核心代码不改。
- G5 交付形态与现网一致：单二进制 + `go:embed` 前端 + fnOS FPK，升级不丢数据。
- G6 前端可维护：组件化、有设计令牌、能出截图回归。

### 3.2 非目标（明确不做）

- N1 **不做多用户/多租户**：单用户自用，不做计费、注册、权限体系。
- N2 **不做上游协议的主动对抗**：上游加闸门就摘渠道，不做绕过封控的军备竞赛。
- N3 **不追求渠道数量**：首发 3 个渠道（QoderCN / WorkBuddyCN / TraeWork）；千问办公、QoderCOM、WorkBuddyAI 按实测裁定为「暂停」——适配器位置保留但不下发模型，按实际可用性手动启停。
- N4 **不做移动端原生 App**：响应式 Web 即可（现有面板在手机上能用是加分项）。
- N5 **不做账号自动注册/接码**：只支持用户已有的账号登录。
- N6 **不做多用户体系**：不做注册、找回密码、角色权限；管理员密码是唯一凭证，忘记则命令行重置。

## 4. 功能需求

优先级：**P0** = 没有它产品不成立；**P1** = 第一版要有；**P2** = 可延后。

### 4.1 账号池（Pool）— P0

| ID | 需求 | 验收标准 |
|---|---|---|
| F1.1 | 多渠道多账号并存，按渠道分组管理 | 面板能按渠道看到每个账号的昵称/余额/状态 |
| F1.2 | 登录接入：OAuth 设备流 / 授权码 / 扫码，浏览器回调自动绑号 | 从点「＋」到账号出现在列表 < 3 分钟，无需手工粘贴 token |
| F1.2a | 授权**失败必须给出原因**：错误分类 + 上游原话，不是「请重试」 | 失败屏必显示 `kind` 与上游原报文摘要，并落一条流水 |
| F1.3 | 凭证本地加密存储，永不进入日志、导出、错误信息 | 全量日志正则扫描无 token/refresh_token 命中 |
| F1.4 | 粘性路由：同一会话尽量落同一账号，减少风控 | 连续 10 次同会话请求，路由到同一 uid |
| F1.5 | 轮转：失败自动换号重试（上限可配），换号后清除粘性 | 单号故障时请求仍成功，日志显示换号路径 |
| F1.6 | 冷却与熔断：按错误类型分档冷却（额度/限流/会话失效/上游故障） | 429 冷却 60s；额度不足冷却 12h；会话失效直接禁用 |
| F1.7 | 余额与到期感知：余额、赠送额度、到期时间 | 面板显示「剩余 X 积分 · Y 到期」，可按余额排序 |
| F1.7a | **凭证自动续期**：临期/过期时用 refresh_token 换新，401 时先续期再重试 | 续期成功不误禁用账号；续期失败给出「需重新授权」并附带上游原话；换出的新 refresh token 必须落盘（上游会轮换） |
| F1.8 | 签到与保活：渠道支持则自动签到；定时保活防掉线 | 签到结果可查；无签到活动的渠道明确标注「无活动」 |
| F1.9 | 账号启停：手动禁用/启用，禁用原因可见 | 禁用后不再参与路由，面板显示原因 |

### 4.2 渠道适配器（Channel Adapter）— P0

| ID | 需求 | 验收标准 |
|---|---|---|
| F2.1 | 适配器接口统一：`RefreshToken / ChatStream / FetchModels / FetchPricing / Resource / Checkin / Classify` | 新增渠道只需实现该接口 + 注册一行 |
| F2.2 | **能力声明**（capability descriptor）：支持 tools / 图片 / 推理 / 上下文窗口 / 是否 SSE-only | 面板能按能力位渲染图标；网关据此做请求清洗与能力降级 |
| F2.3 | 渠道级开关与状态：可用 / 暂停 / 维护中，暂停渠道不下发模型 | `/v1/models` 不出现暂停渠道的模型 |
| F2.4 | 协议差异隔离在适配器内：签名（COSY 等）、信封剥壳、SSE 形态转换 | 核心层只见到标准 OpenAI chunk |
| F2.5 | 三家首批适配器：QoderCN、WorkBuddyCN、TraeWork | 三个渠道真实对话均出字，模型列表与上游一致 |

### 4.3 兼容网关（Gateway）— P0

| ID | 需求 | 验收标准 |
|---|---|---|
| F3.1 | `POST /v1/chat/completions`（流式 + 非流式） | OpenAI SDK 直连可用 |
| F3.2 | `POST /v1/messages` + `/v1/messages/count_tokens`（Anthropic 兼容） | Claude Code 直连可用 |
| F3.3 | `POST /v1/responses`（Codex 兼容） | Codex 直连可用 |
| F3.4 | `GET /v1/models`，标识渠道前缀与能力位 | 与面板展示一致 |
| F3.4.1 | 面板给出客户端应填的「对外基址」 | 按实际监听地址与访问主机名推断、一键复制，不用用户自己拼字符串 |
| F3.5 | 多 API Key 分层：普通 key / 管理 key，可吊销 | 管理端操作不接受普通 key；面板可直接看掩码/按需显示明文/一键轮换，轮换后旧 Key 立即失效（不必登服务器看 config.json） |
| F3.6 | **流式错误必须回传**：header 未发出 → 结构化错误；已发出 → 错误帧 + `[DONE]` | 故意打坏上游，客户端必须报错而不是静默 |
| F3.7 | 请求清洗：不支持的参数、图片、工具调用按能力位降级或明确拒绝 | 明确拒绝时返回可读原因，不静默丢弃 |

### 4.4 模型目录与费率（Catalog）— P1

| ID | 需求 | 验收标准 |
|---|---|---|
| F4.1 | 动态模型表：从上游拉取 + 静态兜底 + 缓存 | 上游不可达时仍能出模型表（标注为兜底） |
| F4.2 | 能力位与上下文窗口：来自上游则标注来源，否则显示「未知」不猜数字 | 面板区分「上游值 / 估算值 / 未知」 |
| F4.3 | 费率与倍率：展示倍率、促销标签 | 与上游 `/api/chat-modes` 一致 |
| F4.4 | 模型级可用性标记：由健康探测产生，不是配置写死 | 挂死模型（如 `deepseek-v4.1-flash`）自动标注并可从下发列表剔除 |
| F4.5 | **只下发可用模型**（设置里可开）：开启后 `/v1/models` 不返回体检失败的模型 | 客户端模型列表里不出现挂死的模型；未体检的照常返回（「不知道」不等于「不可用」）；面板仍逐条列出并说明原因；只影响列表，直连调用不拦 |

### 4.5 健康与自检（Health）— P0

| ID | 需求 | 验收标准 |
|---|---|---|
| F5.1 | **真实抽样探测**：每渠道取代表模型发真实请求，收到内容才算通过 | 空流 / 错误信封 / 超时一律判失败，并给出上游原话 |
| F5.2 | 渠道健康状态：可用 / 降级 / 故障 / 暂停，附原因与最后成功时间 | 千问办公这类上游闸门必须显示为「故障·上游」，不能是绿色 |
| F5.3 | 测速：并发测延迟（TTFT），结果可持久化、可对比 | 结果区分 ok / error，error 带原因 |
| F5.4 | 定时体检 + 变更后体检 | 升级后自动跑一次并给出结论 |
| F5.5 | 健康判据可审计：面板能看到「上次为什么判它坏」 | 保留最近 N 次探测结论 |

### 4.6 可观测与运维（Ops）— P1

| ID | 需求 | 验收标准 |
|---|---|---|
| F6.1 | 请求流水：时间、渠道、账号、模型、状态、耗时、TTFT、错误分类 | 可按渠道/状态/时间过滤；单页可查最近 500 条 |
| F6.2 | 错误分类聚合：把上游五花八门的错误归一成有限几类并计数 | 一眼看出「今天 78% 失败是上游 503」 |
| F6.3 | 面板「一键诊断」：给定模型/渠道，输出「本地配置 OK / 上游故障」结论 + 原始报文 | 千问办公这类问题 30 秒定位，不需手工抓包 |
| F6.4 | 配置管理：监听、API Key、并发、冷却策略、签到时间、保活 | 改完即时生效，可回滚；监听地址需重启生效，且启动脚本已显式指定 `-addr` 时以启动参数为准（面板显示「当前实际监听」，不能让人改了以为生效） |
| F6.5 | 日志分级与轮转，敏感信息脱敏 | 日志体积有上限，不撑爆磁盘 |
| F6.6 | 数据备份与恢复：账号、配置、历史可导出/导入 | 升级 FPK 不丢数据（沿用现网数据目录约定）；导入失败必须说明原因（跨应用凭证目录默认 0600 读不了时给出绕行办法），且导入后无需重启即可见 |
| F6.7 | 面板内修改管理员密码（需当前密码） | 改完其它设备的会话立即失效、当前浏览器保持登录；忘记密码仍只能走命令行 `poolgate admin reset-password` |

| ID | 需求 | 验收标准 |
|---|---|---|
| F7.1 | 七屏信息架构：**登录 / 授权** + 总览 / 账号 / 模型 / 测速 / 日志 / 设置 | 见 `prototype/07-login.html` 及其余六屏 |

| F7.3 | 状态永不只用颜色表达：图标 + 文字 + 颜色 | 色觉障碍下仍可辨（原型已按此实现） |
| F7.4 | 数值可对齐：金额/延迟/计数用等宽数字 | 表格列右对齐，数字不跳动 |
| F7.5 | 响应式：手机竖屏可用（至少能看状态、开关账号） | 390px 宽下**页面本身**无横向滚动；宽表格在卡片内横向滚动、按钮不换行（原型已按此验证） |
| F7.6 | 危险操作二次确认（删除账号、吊销 Key、清空日志） | 确认文案写明后果 |

| 类别 | 要求 |

| 兼容 | 保留 wild-work 的数据目录约定（`/vol6/@appdata/poolgate` 等），迁移脚本可回退 |

## 6. 验收标准（整体）

达成以下全部，即视为第一版成功：

1. **真流量**：Studio / Claude Code 通过本服务连续对话 30 分钟无中断。
2. **失败可见**：人为把某渠道上游打断，客户端立即收到明确错误，面板 30 秒内显示原因（当前 wild-work 做不到）。
3. **判据可信**：面板全绿 ⇔ 抽样真实请求全部出字，二者不得背离。
4. **可插拔**：移除一个渠道后，其它渠道与网关无需改一行代码即可继续工作。
5. **升级无损**：FPK 升级后账号、配置、历史完整保留。
6. **可读性**：新接手的人只看面板就能回答「哪个渠道能跑、为什么某个渠道挂了」。
7. **登录闭环**：首次安装 → 设置密码 → 加号授权 → 客户端出字，全程在面板内完成，无需手工粘贴 token。

## 7. 风险与依赖

| 风险 | 影响 | 应对 |
|---|---|---|
| 上游继续改版（千问办公式） | 渠道随时失效 | 架构按「摘除是常态」设计；能力声明 + 暂停开关；体检定时化 |
| 上游加风控/限流 | 请求失败率上升 | 粘性路由 + 分档冷却 + 请求清洗；不做对抗性绕过 |
| 账号来源不稳定 | 池子枯竭 | 面板把「还能撑多久」做成第一屏指标 |
| 自用项目易烂尾 | 投入打水漂 | 里程碑按「每个里程碑都能独立交付可用物」切分（见设计方案 §9） |

**依赖**：fnOS 应用环境（`/vol6/@appcenter`、`@appdata`、`@appconf` 约定）；Go 工具链；Playwright/Chromium（UI 截图回归）。
