## 4. 千问办公故障定位（可作为「上游问题 vs 本地问题」判定的样板）

**现象**：登录、token 刷新、余额、模型列表全部正常；只有对话失败。面板测速显示绿色。

**定位过程（三步，均已在 2026-09-24 复现）**

| 步骤 | 做法 | 结果 |
|---|---|---|
| 1 | 从 NAS 读取该账号凭证（`/vol6/@appconf/wildwork/auth/qwenwork-*.json`） | 拿到 OAuth JWT |
| 2 | 手搓 COSY 签名直连上游网关（绕过 wild-work） | `GET /api/v2/model/list` → **200**，qwork scene 正常 ⇒ 签名与目录接口没问题 |
| 3 | 同签名 POST 推理端点 | 正确档位（`pro`/`flash`/`qwork-advanced`）→ **信封 503 `Model catalog unavailable`**；错误档位 → **信封 403 `Model is not available for this user`** ⇒ 档位校验通过，卡在路由之前的服务端闸门 |

**补充排除**（本次新做）：路径段变体（`service/{pro,qwork,auto,chat,flash,v3,v1}`）→ 只有 `pro` 是有效路由，其余 404；
`AgentId` 变体（`agent_common`/`agent_qwork`/`agent_default`）→ 全部 503。**与 AgentId 无关。**

**上游确认**：`rockswang/wild-work` **Issue #31**（2026-09-23，open）现象逐字一致；
作者回复 *"估计千问办公改版了，过几天看看上游逆向项目会不会更新吧"*。
仓库内 `docs/千问办公QwenWork逆向对比备忘.md` §10 另记有 8 轮客户端维度排除矩阵（签名/token/机器指纹/档位/body/版本头/UA/22 头克隆/info/query），全部 503。

**结论**：**上游改版导致的服务端闸门，客户端无可修之处。** 网页版同账号可用是因为它走
`qwenwork.cn` 的 `/api/chat-ws`（WebSocket + cookie），不经过桌面网关。

**PoolGate 的处理**：渠道标 `Paused`，面板显示「故障·上游」+ 原因与上游原话，
模型不下发给客户端。适配器实现位置保留，等上游逆向社区更新后可快速恢复。

> **2026-09-25 追加（鉴权口径，实测踩到）**：网页域 `qwenwork.cn` 的
> `Cookie: token=<JWT>` 里那个 JWT 必须是桌面网关换发的 **device_token**，
> 不是 OAuth 授权码兑换出来的 access token —— 后者打网页域一律
> `401 {"code":"invalid-credential","msg":"Invalid JWT token"}`（面板表现是
> 「授权成功但每次取余额/对话都 401，重新登录多少次都一样」）。
> 拿 device_token 的入口是 `POST https://gateway.qwenwork.cn/api/v1/deviceToken/refresh`
> （body `{"refresh_token": "...", "target": "c"}`，返回 `{token, device_token, refresh_token, expires_in(ms)}`）。
> 该端点**没有**被 503 闸门影响（闸门只在推理端点）。wild-work 的 `qwenwork.RefreshToken`
> 就是这么写的，其备忘亦记有「OAuth 兑换的首个 token 调 /user/info 会 401 invalid-credential」。

## 6. 对 PoolGate 的直接输入

1. **首发适配器**：QoderCN、WorkBuddyCN、TraeWork。
2. **模型级健康**必须做：TraeWork 单渠道内既有 2.0s 的正常模型，也有 >230s 挂死的模型，
   渠道级开关粒度不够。
3. **错误分类要区分「上游故障」与「账号故障」**：千问办公的 503 是渠道级，
   若计入账号错误会把好号也冷却掉。
4. **测速与体检共用判据**：本次 90 模型测速的假绿，直接证明了只看状态码的判据不能用。

## 7. 登录式渠道（0.4.9 / 0.5.0 新增）

本批渠道的共同前提：**凭证来自用户自己浏览器里的登录态**，粘一次即可。
服务端不与登录接口打交道 —— 不存密码、不在 NAS 上跑无头浏览器（这是选型红线）。

| 渠道 | 用户粘什么 | 上游协议 | tools | 推理 | 参考实现 | 验证状态 |
|---|---|---|---|---|---|---|
| `deepseek` | `userToken`（localStorage） | agent 协议 + p/o/v patch 流；每轮解官方 WASM PoW | ⛔ toolshim | ✅ THINK 片段 | ds-free-api | mock 端到端 + 真 WASM ABI 自测 |
| `kimi` | refresh token（或 access token） | **Connect（gRPC-Web）**：5 字节信封 + JSON 帧流 | ⛔ toolshim | ✅ `block.think` | kimi2api | mock 端到端（含逐字节半帧） |
| `chatglm` | cookie `chatglm_refresh_token` | SSE + **每请求自算签名**（时间戳变换 + md5） | ⛔ toolshim | ✅ item `type=think` | GLM-Free-API | mock 端到端 |
| `doubao` | 整行 Cookie（含 `sessionid`） | 带事件名的 SSE；思考靠 `block_type=10040` 开关块 | ⛔ toolshim | ✅ 开关块之间 | doubao2api | mock 端到端 |
| `yuanbao` | 请求头 `x-uskey` | SSE；`type=think` / `type=text` 分流 | ⛔ toolshim | ✅ `type=think` | yuanbao-free-api + yuanbao-chat2api（两份交叉验证） | mock 端到端 |
| `chatgpt` | `accessToken`（JWT） | sentinel 挑战 + 自算 PoW；`/backend-api/conversation` 的 SSE patch 流 | ⛔ toolshim | ✅ `/message/content/thoughts/*` | ChatGPT2API-GO + gpt4free | mock 端到端（含 PoW 复算） |
| `anthropic` | OAuth 授权码（订阅登录） | Messages API：SSE 事件流 | ✅ 原生 | ⛔ 不主动开思考（见下） | 订阅 OAuth 的公开实现 | mock 端到端 |
| `codebuddy` | 浏览器授权（同 WorkBuddy 的 state 轮询） | OpenAI 兼容 SSE（**后端只接受流式**） | ✅ 原生 | ✅ | codebuddy2openai + workbuddy2api-hub | mock 端到端 |
| `copilot` | GitHub **设备码**（浏览器输码） | 标准 OpenAI 协议（需伪装 VS Code 插件头） | ✅ 原生 | ⛔ 上游无思考字段 | copilot-api | mock 端到端 |
| `kiro` | 刷新令牌（桌面版 / 企业版三件套） | **AWS Event Stream 二进制帧**（不是 SSE） | ✅ 原生 | ⛔ 上游无思考字段 | kiro-gateway | mock 端到端（含半包） |
| `iflow` | `~/.iflow/settings.json` 里的 apiKey | OpenAI 兼容 SSE + **每请求 HMAC-SHA256 签名** | ✅ 原生 | ✅ `reasoning_content` | iflow2api | mock 端到端（签名复算） |
| `lingma` | IDE 登录缓存（`cache/user`、`cache/id`） | 双层嵌套 SSE（外层 body + 内层 OpenAI 形态） | ✅ 原生 | ⛔ | lingma-proxy | mock 端到端（AES 解密 + 签名复算） |
| `antigravity` | OAuth 授权码（Google） | `v1internal:streamGenerateContent`（Gemini 风格，外层包 `response`） | ✅ 原生 | ✅ | opencode-antigravity-auth | mock 端到端 |
| `windsurf` | Windsurf/Devin 客户端的 session token | protobuf / Connect 流式帧（**只走直连云那条路**） | ⛔ toolshim | ✅ 字段 #12 | WindsurfAPI | mock 端到端（含 protobuf 往返与半包） |

说明：

- **验证状态的含义**：这批渠道的协议都是按**公开参考实现**移植的（本机网络到不了这些上游的登录
  接口，也没有可用的真实账号），所以「mock 端到端」只证明**我们的解析与上游形态一致**，
  不证明上游当前仍长这样。真上游验收需要用户粘一次凭证；第一次对话若失败，错误信息里会带上上游原话。
- **能力位为什么都是 `tools=⛔`**：这几家的网页协议都没有原生工具调用（元宝/豆包的参考实现
  明确写了不支持 Function Calling），但网关会用 toolshim 把工具定义翻成提示词、再把模型输出的
  标记解析回结构化 `tool_calls` —— 对客户端合同不变，所以面板上标注的是「工具调用靠网关模拟」。

### 各渠道的已知限制（使用前要知道的事，不是免责声明）

| 渠道 | 已知限制 |
|---|---|
| `chatgpt` | 对话前要过 sentinel 挑战并自算 PoW（sha3-512）；**Turnstile 解不出时明确报错**（不静默降级成空 token）；`arkose.required=true` 时直接失败（参考实现也没实现它）。模型 slug 会漂移，默认用 `auto` 最稳 |
| `anthropic` | 走**订阅 OAuth**（不是 API Key）：官方明确禁止第三方客户端使用订阅令牌，**有封号风险**；本机出口 IP 被 Anthropic 403（`docs/05` 有实测记录），要用得配出口代理 |
| `copilot` | 必须伪装 VS Code 的 Copilot 插件（版本号是常量，上游收紧时会过期）；GitHub 设备码页**没有**能把 user_code 带在地址里的变体，所以码是通过面板的引导语显示的 |
| `kiro` | 上游是 AWS Event Stream 二进制帧，不是 SSE（切帧要容忍半包）；`runtime.{region}.kiro.dev` 不提供模型目录接口，档位是本地白名单 |
| `windsurf` | **只走直连云那条路**（不走需要本地语言服务器的 Cascade）；工具定义的两个 protobuf 子 tag 未标定 → 声明为 toolshim 模拟而不是猜 tag |
| `antigravity` | 授权后**必须做开通**（`loadCodeAssist` / `onboardUser`），少这一步会 412/403；免费档不能带 project |
| `lingma` | 凭证要服务端解密（AES-128-CBC，密钥来自 machineID 前 16 字节）；远端流**不带真实 usage**（我们不伪造 token 数） |
| `iflow` | 每请求要带 HMAC-SHA256 签名，UA 必须是 `iFlow-Cli`（UA 是解锁高级模型的关键） |

### 风险（写在这里，因为这决定了它们能不能当主力）

| 风险 | 具体表现 | 处置 |
|---|---|---|
| **封号** | 这几条都是「第三方客户端复用登录态」，各上游 ToS 都禁止；参考实现的 README 普遍有明文警告 | 别用主力账号；每账号最小间隔出厂默认 2–5 秒（`Spec.DefaultMinIntervalSec`），配合一账号一出口 |
| **请求签名** | 智谱的签名算法与密钥**会随官网改版变化**（参考实现源码里就写着「官网变化记得更新」） | 密钥可由凭证 `Extra["sign_secret"]` 覆盖，不用改代码；签名失效时归一成可见错误并带上游原话 |
| **风控** | 豆包的 `a_bogus` 由浏览器 fetch hook 现算，纯 HTTP 路径**不带它** → 可能被风控要求人工验证码（710022004/710022002） | **不伪造签名**；风控码归一成「去浏览器过验证码后重新粘贴 Cookie」，而不是含糊的「上游故障」 |
| **凭证过期** | Kimi/智谱有 refresh 链路（服务端自动续）；豆包/元宝没有（失效只能重新粘） | 面板的粘贴引导语写明各渠道的差异；401 一律归一成 `SessionDead`，账号状态可见 |
