## 4. 千问办公故障定位（可作为「上游问题 vs 本地问题」判定的样板）

**现象**：登录、token 刷新、余额、模型列表全部正常；只有对话失败。面板测速显示绿色。

**定位过程（三步，均已在 2026-09-24 复现）**

| 步骤 | 做法 | 结果 |
|---|---|---|
| 1 | 从 NAS 读取该账号凭证（`/vol6/@appconf/wildwork/auth/qwenwork-*.json`） | 拿到 OAuth JWT |
| 2 | 手搓 COSY 签名直连上游网关（绕过 wild-work） | `GET /api/v2/model/list` → **200**，qwork scene 正常 ⇒ 签名与目录接口没问题 |
| 3 | 同签名 POST 推理端点 | 正确档位（`pro`/`flash`/`qwork-advanced`）→ **信封 503 `Model catalog unavailable`**；错误档位 → **信封 403 `Model is not available for this user`** ⇒ 档位校验通过，卡在路由之前的服务端闸门 |

**补充排除**（本次新做）：路径段变体（`service/{pro,qwork,auto,chat,flash,v3,v1}`）→ 只有 `pro` 是有效路由，其余 404；
`AgentId` 变体（`agent_common`/`agent_qwork`/`agent_default`）→ 全部 503。**与 AgentId 无关。**

**上游确认**：`rockswang/wild-work` **Issue #31**（2026-09-23，open）现象逐字一致；
作者回复 *"估计千问办公改版了，过几天看看上游逆向项目会不会更新吧"*。
仓库内 `docs/千问办公QwenWork逆向对比备忘.md` §10 另记有 8 轮客户端维度排除矩阵（签名/token/机器指纹/档位/body/版本头/UA/22 头克隆/info/query），全部 503。

**结论**：**上游改版导致的服务端闸门，客户端无可修之处。** 网页版同账号可用是因为它走
`qwenwork.cn` 的 `/api/chat-ws`（WebSocket + cookie），不经过桌面网关。

**PoolGate 的处理**：渠道标 `Paused`，面板显示「故障·上游」+ 原因与上游原话，
模型不下发给客户端。适配器实现位置保留，等上游逆向社区更新后可快速恢复。

> **2026-09-25 追加（鉴权口径，实测踩到）**：网页域 `qwenwork.cn` 的
> `Cookie: token=<JWT>` 里那个 JWT 必须是桌面网关换发的 **device_token**，
> 不是 OAuth 授权码兑换出来的 access token —— 后者打网页域一律
> `401 {"code":"invalid-credential","msg":"Invalid JWT token"}`（面板表现是
> 「授权成功但每次取余额/对话都 401，重新登录多少次都一样」）。
> 拿 device_token 的入口是 `POST https://gateway.qwenwork.cn/api/v1/deviceToken/refresh`
> （body `{"refresh_token": "...", "target": "c"}`，返回 `{token, device_token, refresh_token, expires_in(ms)}`）。
> 该端点**没有**被 503 闸门影响（闸门只在推理端点）。wild-work 的 `qwenwork.RefreshToken`
> 就是这么写的，其备忘亦记有「OAuth 兑换的首个 token 调 /user/info 会 401 invalid-credential」。

## 6. 对 PoolGate 的直接输入

1. **首发适配器**：QoderCN、WorkBuddyCN、TraeWork。
2. **模型级健康**必须做：TraeWork 单渠道内既有 2.0s 的正常模型，也有 >230s 挂死的模型，
   渠道级开关粒度不够。
3. **错误分类要区分「上游故障」与「账号故障」**：千问办公的 503 是渠道级，
   若计入账号错误会把好号也冷却掉。
4. **测速与体检共用判据**：本次 90 模型测速的假绿，直接证明了只看状态码的判据不能用。

说明：

- **验证状态的含义**：这批渠道的协议都是按**公开参考实现**移植的（本机网络到不了这些上游的登录
  接口，也没有可用的真实账号），所以「mock 端到端」只证明**我们的解析与上游形态一致**，
  不证明上游当前仍长这样。真上游验收需要用户粘一次凭证；第一次对话若失败，错误信息里会带上上游原话。
- **能力位为什么都是 `tools=⛔`**：这几家的网页协议都没有原生工具调用（元宝/豆包的参考实现
  明确写了不支持 Function Calling），但网关会用 toolshim 把工具定义翻成提示词、再把模型输出的
  标记解析回结构化 `tool_calls` —— 对客户端合同不变，所以面板上标注的是「工具调用靠网关模拟」。

### 各渠道的已知限制（使用前要知道的事，不是免责声明）

| 渠道 | 已知限制 |
|---|---|
| `chatgpt` | 对话前要过 sentinel 挑战并自算 PoW（sha3-512）；**Turnstile 解不出时明确报错**（不静默降级成空 token）；`arkose.required=true` 时直接失败（参考实现也没实现它）。模型 slug 会漂移，默认用 `auto` 最稳 |
| `anthropic` | 走**订阅 OAuth**（不是 API Key）：官方明确禁止第三方客户端使用订阅令牌，**有封号风险**；本机出口 IP 被 Anthropic 403（`docs/05` 有实测记录），要用得配出口代理 |
| `copilot` | 必须伪装 VS Code 的 Copilot 插件（版本号是常量，上游收紧时会过期）；GitHub 设备码页**没有**能把 user_code 带在地址里的变体，所以码是通过面板的引导语显示的 |
| `kiro` | 上游是 AWS Event Stream 二进制帧，不是 SSE（切帧要容忍半包）；`runtime.{region}.kiro.dev` 不提供模型目录接口，档位是本地白名单 |
| `windsurf` | **只走直连云那条路**（不走需要本地语言服务器的 Cascade）；工具定义已走**原生**——参考实现用付费实弹（2026-07-04，teams 账号 claude-opus-4-8）标定了 ToolDef 的内部 tag：外层 #10、`name=1 / description=2 / parameters=3`（`WindsurfAPI/src/devin-connect.js` 的 `DEFAULT_DEF_TAGS`）；响应侧工具调用在 #6 |
| `antigravity` | 授权后**必须做开通**（`loadCodeAssist` / `onboardUser`），少这一步会 412/403；免费档不能带 project |
| `lingma` | 凭证要服务端解密（AES-128-CBC，密钥来自 machineID 前 16 字节）；远端流**不带真实 usage**（我们不伪造 token 数） |
| `iflow` | 每请求要带 HMAC-SHA256 签名，UA 必须是 `iFlow-Cli`（UA 是解锁高级模型的关键） |

### 风险（写在这里，因为这决定了它们能不能当主力）

| 风险 | 具体表现 | 处置 |
|---|---|---|
| **封号** | 这几条都是「第三方客户端复用登录态」，各上游 ToS 都禁止；参考实现的 README 普遍有明文警告 | 别用主力账号；每账号最小间隔出厂默认 2–5 秒（`Spec.DefaultMinIntervalSec`），配合一账号一出口 |
| **请求签名** | 智谱的签名算法与密钥**会随官网改版变化**（参考实现源码里就写着「官网变化记得更新」） | 密钥可由凭证 `Extra["sign_secret"]` 覆盖，不用改代码；签名失效时归一成可见错误并带上游原话 |
| **风控** | 豆包的 `a_bogus` 由浏览器 fetch hook 现算，纯 HTTP 路径**不带它** → 可能被风控要求人工验证码（710022004/710022002） | **不伪造签名**；风控码归一成「去浏览器过验证码后重新粘贴 Cookie」，而不是含糊的「上游故障」 |
| **凭证过期** | Kimi/智谱有 refresh 链路（服务端自动续）；豆包/元宝没有（失效只能重新粘） | 面板的粘贴引导语写明各渠道的差异；401 一律归一成 `SessionDead`，账号状态可见 |

## 8. 0.6.0 逐渠道核对与实测记录（2026-09-26）

### 8.1 做法

22 个渠道**逐个**与公开开源参考实现（以及上一代 `wild-work` 实现）**逐字段核对**：端点、URL query、
请求头（含伪装版本号）、请求体每个字段的名字与形态（空串 / null / 缺省）、流帧解析、结束条件、
错误归一、模型表。每处改动都在代码注释里写明依据（参考实现文件名 + 行号）。

参考实现先核实过时效性（逐个与上游 HEAD 比对），另外从 GitHub 扫到并引入了更近的实现做交叉验证：
`AIClient2API`（8.8k★，独立实现 Antigravity / Kiro / iFlow / Qwen）、新版 `doubao2api`、
`codebuddy2api`、`Qoder-2API-Go`、`Orchids-2api`、`workbuddy-openai-proxy`、`BYOKEY` 等。

### 8.2 真实凭证实测（现网账号）

| 渠道 | 结果 | 说明 |
|---|---|---|
| `doubao` | ✅ 真出字 | 流式 / 深度思考 / 工具调用三条路径都验过。**修前**复现上游 `710020202 common invalid param`（请求体 id 字段为空串），照参考实现补齐后同一条 Cookie 正常出字 |
| `qodercn` | ✅ 真出字 | `auto` 正常；工具调用返回 `finish_reason=tool_calls` + 参数 |
| `workbuddy` | ✅ 真出字 | `hy3` 正常；工具调用同上；**脱敏修复后**带 Claude Code 身份句的请求也能正常出字（见 8.3.2） |
| `qwenwork` | ✅ 真出字 | `pro` 正常（该渠道自 0.3.9 起走 device_token） |
| `traework` | ⚠️ 账号额度耗尽 | 鉴权 / 刷新 / 目录（28 个模型）正常；对话时上游在流里回 `event:error {"code":4008,"message":"Your requests have exceeded the quota."}`（`cn_credits:0`）。**不是代码问题**，本版把这类流内错误如实归一成 `HardCredit` 并带上游原话 |

### 8.3 核对出来的典型问题（按影响排序）

#### 8.3.1 请求体字段形态不对 → 整条渠道不可用

- **豆包**：`local_conversation_id` / `local_message_id` / `block_id` 是空串、缺 `is_finish` /
  `patch_type` / `icon_url` 等键 → 上游回 `710020202 common invalid param`。
- **Gemini（Code Assist）**：外层信封多发了 `user_prompt_id`、内层多发了 `session_id` ——
  三份参考实现都没有这两个字段，Google 的 JSON 解析对未知字段会直接 400（`Cannot find field`）。

#### 8.3.2 「移植丢失」：wild-work 里有、重做时整块没搬过来的防护

这类问题不是"某个字段写错"，而是**整套防线不见了**，后果往往是"用着用着整个不能用了"：

1. **出站请求体指纹脱敏（新补 `internal/sanitize`）** —— 上游（CodeBuddy / WorkBuddy 后端）
   对请求体里 Claude Code / Codex CLI 注入的模板句做**逐字精确黑名单匹配**，命中就回
   `HTTP 400 code=11128 "Illegal API invocation from an unapproved channel"`。
   即**从 Claude Code / Studio 调这两个渠道会被上游按安全策略挡掉**。
   本版照 wild-work 原样移植（策略是**最小改写**：键值型指纹整段删、承载语义的模板句只换一个词，
   不改动用户的实质指令），接到 `workbuddy` / `workbuddyai` / `codebuddy` 三个渠道的请求体组装处。
   **真上游 A/B 实测**（2026-09-26，现网 WorkBuddy 账号）：

   | 版本 | 同一条请求（system 含 `You are Claude Code, Anthropic's official CLI for Claude.`） |
   |---|---|
   | 脱敏前 | ✗ `ContentBlocked` — `{"code":11128,"msg":"Illegal API invocation from an unapproved channel"}` |
   | 脱敏后 | ✓ 出字「你好」 |

   第三方佐证：`workbuddy-openai-proxy` 的 `CLIENT_FINGERPRINTS`、`Orchids-2api` 的
   `CodePolicyBlocked = 11128`（两份独立实现各自绕过同一道闸门）。

2. **孤儿 tool_call ↔ tool 结果配对清理** —— OpenAI 兼容协议要求带 `tool_calls` 的 assistant
   消息每个 id 都有对应的 `role:tool` 结果，缺一侧上游 400 拒绝整个请求。工具执行失败时客户端
   常把 tool_calls 存进历史却写不回结果，这条坏历史每次重放都 400 → **整条会话报废**。
   本版在网关发出上游之前清理无法配对的条目（wild-work `internal/upstream/tool_pairing.go`）。

3. **工具调用残缺参数检测** —— 流被截断（连接中断 / `finish_reason==length`）时
   `tool_calls[].function.arguments` 只剩半截 JSON，原样给客户端会让它解析失败并卡死会话。
   判据与 wild-work 一致：**只把「非空但无法解析成 JSON」视为截断**（空串是合法的无参工具）。

#### 8.3.3 静默丢字（红线一的另一种形态）

- **ChatGPT 网页版**：上游的 patch 流里有一种「只有 `v`、没有 `p`/`o`」的省略路径增量帧，
  三份参考实现都专门处理了它；我们原来直接忽略 → **正文会被静默丢字**（显示出来就是缺词断句，
  而且日志里什么都不说）。

#### 8.3.4 上游原话被吞

- 适配器从流里抛出的**普通 error** 会被网关换成一句通用的「上游请求失败」——
  TraeWork 的额度耗尽就是这么变成「解析失败」的（客户端既定位不了原因，账号健康判定也失去依据）。
  本版：①各适配器的流内错误一律归一成带 Kind + 上游原话的 `errs.Error`；
  ②网关对非结构化错误也会把 `err.Error()`（截断 300 字）带进 message 与 upstream 字段。

#### 8.3.5 端点 / 域名打错

- **QoderCOM**：模型目录打到了推理网关（api1），而 COM 是双域名（模型表 api2 / 推理 api1）→
  目录拉不回来，模型 key 全部退化成"客户端名原样透传"。
- **Gemini**：开通长任务轮询走了一个**没有任何参考实现用过**的 `GET /v1internal/{name}`，
  三份参考实现都是**重发同一个 `onboardUser`**。

### 8.4 仍未真上游验证的渠道

13 家登录式渠道里，**只有豆包**在本机有可用凭证并完成了真上游验证；其余渠道的协议都是
「按公开参考实现移植 + mock 端到端」，需要用户自己粘一次凭证才能确认。
第一次使用某个渠道若失败，错误信息里会带上**上游原话**（这是 8.3.4 那个修复的直接收益）。
