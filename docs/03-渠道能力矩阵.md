## 4. 千问办公故障定位（可作为「上游问题 vs 本地问题」判定的样板）

**现象**：登录、token 刷新、余额、模型列表全部正常；只有对话失败。面板测速显示绿色。

**定位过程（三步，均已在 2026-09-24 复现）**

| 步骤 | 做法 | 结果 |
|---|---|---|
| 1 | 从 NAS 读取该账号凭证（`/vol6/@appconf/wildwork/auth/qwenwork-*.json`） | 拿到 OAuth JWT |
| 2 | 手搓 COSY 签名直连上游网关（绕过 wild-work） | `GET /api/v2/model/list` → **200**，qwork scene 正常 ⇒ 签名与目录接口没问题 |
| 3 | 同签名 POST 推理端点 | 正确档位（`pro`/`flash`/`qwork-advanced`）→ **信封 503 `Model catalog unavailable`**；错误档位 → **信封 403 `Model is not available for this user`** ⇒ 档位校验通过，卡在路由之前的服务端闸门 |

**补充排除**（本次新做）：路径段变体（`service/{pro,qwork,auto,chat,flash,v3,v1}`）→ 只有 `pro` 是有效路由，其余 404；
`AgentId` 变体（`agent_common`/`agent_qwork`/`agent_default`）→ 全部 503。**与 AgentId 无关。**

**上游确认**：`rockswang/wild-work` **Issue #31**（2026-09-23，open）现象逐字一致；
作者回复 *"估计千问办公改版了，过几天看看上游逆向项目会不会更新吧"*。
仓库内 `docs/千问办公QwenWork逆向对比备忘.md` §10 另记有 8 轮客户端维度排除矩阵（签名/token/机器指纹/档位/body/版本头/UA/22 头克隆/info/query），全部 503。

**结论**：**上游改版导致的服务端闸门，客户端无可修之处。** 网页版同账号可用是因为它走
`qwenwork.cn` 的 `/api/chat-ws`（WebSocket + cookie），不经过桌面网关。

**PoolGate 的处理**：渠道标 `Paused`，面板显示「故障·上游」+ 原因与上游原话，
模型不下发给客户端。适配器实现位置保留，等上游逆向社区更新后可快速恢复。

> **2026-09-25 追加（鉴权口径，实测踩到）**：网页域 `qwenwork.cn` 的
> `Cookie: token=<JWT>` 里那个 JWT 必须是桌面网关换发的 **device_token**，
> 不是 OAuth 授权码兑换出来的 access token —— 后者打网页域一律
> `401 {"code":"invalid-credential","msg":"Invalid JWT token"}`（面板表现是
> 「授权成功但每次取余额/对话都 401，重新登录多少次都一样」）。
> 拿 device_token 的入口是 `POST https://gateway.qwenwork.cn/api/v1/deviceToken/refresh`
> （body `{"refresh_token": "...", "target": "c"}`，返回 `{token, device_token, refresh_token, expires_in(ms)}`）。
> 该端点**没有**被 503 闸门影响（闸门只在推理端点）。wild-work 的 `qwenwork.RefreshToken`
> 就是这么写的，其备忘亦记有「OAuth 兑换的首个 token 调 /user/info 会 401 invalid-credential」。

## 6. 对 PoolGate 的直接输入

1. **首发适配器**：QoderCN、WorkBuddyCN、TraeWork。
2. **模型级健康**必须做：TraeWork 单渠道内既有 2.0s 的正常模型，也有 >230s 挂死的模型，
   渠道级开关粒度不够。
3. **错误分类要区分「上游故障」与「账号故障」**：千问办公的 503 是渠道级，
   若计入账号错误会把好号也冷却掉。
4. **测速与体检共用判据**：本次 90 模型测速的假绿，直接证明了只看状态码的判据不能用。
