## 一句话

把多个 AI 编程助手的**订阅账号**汇成一个池子，对外暴露 **OpenAI / Anthropic 兼容接口**，
并提供一个**能看懂、不会骗人**的控制台。

wild-work 证明了这条路走得通；本项目的任务是把**真正能用的那部分**重做干净——
换掉堆砌式架构、砍掉已废渠道、把「静默失败」从代码里根除。

**0.6.3（2026-09-26）**：**三个新接入的网页渠道（ChatGPT / DeepSeek / 豆包）从"看着能用"变成真能用** ——
用户实测反馈「gpt 报错、豆包读不到上下文、deepseek 回一堆乱码」，查下来是三种不同的病：
① **ChatGPT 网页渠道整条不可用**：turnstile 挑战的 `dx` 必须用**本次请求发出去的 requirements token**
当异或密钥解（旧代码传空串，解出来是 22K 乱码、程序永远跑不出结果，而错误文案谎称「解释器覆盖不到上游
指令集」）；VM 寄存器改按 **JS 属性名**存（上游把 opcode 绑在**小数槽位**上做混淆，`9.23` 与 `9` 是两个
槽位，旧的 `map[int]` 截断后正好砸中程序队列寄存器）；上游现在把消息**摊在 SSE 顶层**（没有外层 `v`），
解析器不认 → 三道门都过、上游正常出字、客户端却拿到**空回复**。修完用现网凭证实测，流式与非流式都真出字。
② **工具调用模拟层两处改进**：格式提醒挪到**对话末尾**（只写在两万字系统提示词里时，豆包 4/4 次都用
自然语言回答、一个工具都不调；挪到末尾后 4/4 正确调用）；解析层开始认模型**自己的原生语法**（DeepSeek 的
DSML、`<function_calls><invoke>`、复数 `<tool_calls>` 外壳），不再把标记泄漏成正文。
③ **网关的判据收紧**：「收到了分片但一个字都没有」现在判失败（以前会回一个空的 200 + `stop`，客户端以为
模型没话说）；顺带修掉 TTFT 在「上游先发一个 role 空帧」时永远记成 0 的问题。
**已知边界（如实写在面板与这里）**：ChatGPT 网页模型会**明确拒绝**按文本协议输出工具调用（它不认为自己
挂载了这些工具），所以该渠道可以当聊天后端用，**还不能当 coding agent 后端**；千问办公不支持工具调用，
网关对它明确拒绝而不是静默丢弃。

## 三条设计红线（来自 wild-work 的实测教训）

1. **零静默失败** —— 任何上游异常都必须在**客户端**可见，并落一条能定位的日志。
   wild-work v2.4.7 修的就是这个：流式分支把上游错误丢掉，客户端拿到 `HTTP 200 + 0 字节`，
   既不回复也不报错，排查方向被带偏好几天。
2. **健康判据必须是「收到了有效内容」**，不是 `HTTP 200`。上游普遍把错误包在 200 的 SSE 信封里，
   看状态码等于没看。
3. **渠道可插拔** —— 新增一个渠道 = 写一个适配器 + 一份能力声明，核心代码零改动。
   上游改版是常态（千问办公就是例子），架构必须让「摘掉一个渠道」是分钟级操作。
